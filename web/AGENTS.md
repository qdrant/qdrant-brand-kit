# Web (for agents)

`@qdrant/web` is Qdrant's website section library: every section a site the size of qdrant.tech needs (navigation, heroes, features, proof, pricing, FAQ, calls to action, listings, footers and more), built from the [design system](../design-system/), with variants, docs and a page builder in the studio's Web page (design lead, 2026-11-21). The qdrant.tech website itself lives in another repo; this is where its sections are designed, documented and reviewed. The work is code-first: a section is built and approved here, and goes to Figma afterwards.

Read these first. Their rules apply here too:

1. The [root `AGENTS.md`](../AGENTS.md).
2. [`design-system/AGENTS.md`](../design-system/AGENTS.md), including which "Never" rules apply to web UI.

## The website's rules

The website's rules (layout, type, color, links, icons, actions, lines, patterns, content) are in [`guidelines.ts`](guidelines.ts), shown first in the studio's Web page, Docs, Guidelines. They're for this repo and for the Hugo build: the dev team and their agents build qdrant.tech from them. Read them all before you build or change a section. Each section's own rules are in its registry entry.

**When the design lead decides a rule for the website, add it to `guidelines.ts` in the same commit as the change** (design lead, 2026-11-22): in its group, as a short title and what it means in practice, with who decided it and when, and where its values live. Change a rule there when it changes. Don't keep a second copy of a rule here; this file says only how to work in this repo.

## How sections are built

- **Import components from `@qdrant/design-system`** and style through tokens and the website's classes in [`styles/web.css`](styles/web.css), loaded after the design system's `globals.css`. A page's root (`<html>` or `<body>`) has `data-web`, `data-context="marketing"` (the design system's accent is indigo by default; marketing makes it amaranth) and a `data-theme`, since menus and dialogs open on `<body>`. A page is all one theme: pages never pass `theme` to a section; it's there for the studio's previews. `Section` sets each section's `data-surface`.
- **Every section has the shared props** from `lib/section.tsx` (`theme`, `surface`, `pattern`, `cardPattern`, `id`, `className`) and takes its content as props, so pages and the builder can fill it. Example content lives in [`content/`](content/): real qdrant.tech copy, verbatim. A slot the site has no copy for stays empty.
- **Use the helpers in `lib/`:** `Section` for every section (theme, surface, padding, the 1200px container or `narrow` or `full`, the rails and seams), `SectionHeader` for a section's kicker, title, text and actions (stacked, split or with an action on the right), `heading` for responsive headings (page, section, statement, card) and `type` for text, `LinkButton` for every call to action, `ArrowLink` for "Read more >" links, `Icon` for Lucide icons named in content, `HexIcon` for a product mark (or a Lucide icon) drawn in small hexagons (`lib/hex-icon.tsx`, exploring: the Products menu), `IconTile` and `toneAt(i)` for icons ([`lib/tone.tsx`](lib/tone.tsx)), `Node` for the hexagon where lines meet inside a section and before kickers, steps and the tabs of a vertical list, never in a row of tabs (`solid` over a line, `active` for the current one, `blink` for a kicker's), `Junction` for the four-point star where a seam meets the rails, its corners filled in the lines' color (`Section` draws it), `Plate` for cards, `Logo`, `CodePanel`, `CopySnippet`, `MediaFrame` for a media slot under review, `ASSETS` for the path to `assets/`, `Code` for code in its syntax colors (`lib/code.tsx`; `CodePanel` and `CopySnippet` use it), `MonoImage` for a one-color image that follows the theme (social marks, badges), `CloudLogo` for the AWS, Google Cloud and Azure logos, and `CustomerLogo` for a customer's logo in its color, light, dark or mono version ([`lib/customer-logo.tsx`](lib/customer-logo.tsx); the list is `content/customer-logos.ts`, the files `assets/logos/customers/`).
- **Cards are `Plate`s** ([`lib/plate.tsx`](lib/plate.tsx)): every card, panel and tile renders `<Plate as="li" …>`, never a div with `web-plate`, so the section's `cardPattern` reaches it. Media (code panels, image slots) keep `web-plate` as a class.
- **Lines and material are classes** in `styles/web.css`: `web-tray` for a framed holder around media, `web-grid` for a hairline grid of cells (it reaches the rails and draws every line in one color), `web-cells` for a row of facts, `web-rule` for a divider, and `web-bleed` on a horizontal line inside a section so it reaches the rails. Use them instead of a new border or fill.
- **Links are classes too:** `web-link` for a text link, `web-link-quiet` for a card title that turns indigo on hover. Colored text takes `--web-indigo-text` or `--web-link`, marks take `--web-indigo` (the values by theme are in `styles/web.css`).
- **Patterns** live in [`patterns/`](patterns/), one file each (see "Adding a pattern"). A section passes `pattern` and `cardPattern` straight to `Section`. Never draw a pattern in a section's own file. A brand pattern from [`brand-assets/patterns/`](../brand-assets/patterns/) renders slowly, so render a section's background once per size, not on every resize.
- **Effects, when they come,** go in the section file with CSS (gradients, blur), in palette colors through their variables, absolutely positioned behind the content, `aria-hidden` and `pointer-events-none`. Never inside a component in `design-system/`. Qbot uses its own glow, `.qd-mascot--glow`.
- **Visuals** go in [`visuals/`](visuals/): product screens rebuilt from the design system (in `data-context="product"`, so their accent is indigo), diagrams and canvas scenes, each a component with its own size that a page passes to a section's `visual` slot (hero, feature grid and rows, case study); the section's frame hugs it, or `visualFrame: "none"` shows it bare. Canvas and WebGL visuals (the zone globe, the depth haze pattern) run on `visuals/scene.tsx`, which reads its colors from the `--web-scene-*` variables in `styles/web.css`, draws only on screen and holds still for reduced motion. A section shows a placeholder (`MediaFrame`) until a page gives it a visual; never ship a placeholder.
- **Images** go in `assets/`, exported from the Figma as they are. A one-color image takes the theme's color through `MonoImage`; the one exception is a logo whose maker has a version for light backgrounds, like `aws-on-light.svg`. Product screens drawn in a Figma are rebuilt with the design system's components (in `data-context="product"`, so their accent is indigo).
- **The lines, the material and indigo are always on** (design lead, 2026-11-24): rails, seams, nodes and hairline grids, plates and trays, and indigo on nodes and links, on every page, with no switch.
- **Style switches** compare the website with and without a decision: `data-web-type="current"` for the type set as it is (the trial type moves into `primitives/typography` if it's kept, with the visual designer's yes). The studio's Canvas, Docs and Builder have them.

- **Proposals** (design lead, 2026-11-24): a new layout to review is a variant with a `proposal` note (what it adds, where the idea comes from) and a new value of the section's `layout` prop, commented as a proposal; a visual enhancement is a switch in the studio's `blocks.tsx` marked `proposal`, off by default, with its CSS in the "Proposals" block of `styles/web.css` under its attribute. Neither is a rule until the design lead keeps it; then it loses its flag, and its rule goes into `guidelines.ts`. A section has four layouts at most.

## Adding a section

1. **The section**: one file in `sections/`, named for what it is (`hero.tsx`, `feature-grid.tsx`), one exported component that takes `SectionProps` plus its content, and passes `theme`, `surface`, `pattern`, `cardPattern`, `id` and `className` to `Section`. Layouts are a prop (`layout`), not separate files. Cards are `Plate`s; icons are `IconTile`s.
2. **Its registry entry**: a file in `registry/` with `defineSection`: its category, a one-line summary, its variants (ready-made props from `content/`, each with a name and a line on when to use it), its docs (when to use it, rules, anatomy, props) and the fields the page builder can edit. Add it to `registry/index.ts`. The studio's canvas, docs and builder read the registry, so a section without an entry doesn't exist for them.
3. **Check it** in the studio's Web page: every variant in the Docs tab, in dark and light, at desktop and phone width, then on the Canvas. Fix what reads wrong, then commit.

**Pages** go in `pages/`, built from the library only: content from `content/<page>.ts`, word for word, and real visuals from `visuals/` passed to the sections' `visual` slot (design lead, 2026-11-22). If a page needs something the library can't do, add it to the section (a prop, a slot) so every page gets it, never a page-only section. The Resilience page (`pages/resilience.tsx`) is the first.

## Adding a pattern

One file in `patterns/` exporting `definePattern({ id, name, kind, description, Layer })`: `kind` is `"background"` (behind a section) or `"surface"` (inside each card). `Layer` is a component that fills its parent (absolute, inset 0), slow (or still) and subtle, in the website's variables, in both themes. List it in `patterns/index.tsx`. It then shows in the studio's Patterns tab, in the builder's pattern pickers, and on any section through `pattern` or `cardPattern`.
